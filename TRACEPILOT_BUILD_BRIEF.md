# TracePilot — Build Brief (for Claude Code)

AI-native incident investigation + deterministic counterfactual replay for distributed backends.

Read this whole file before writing code. Work phase by phase. Do not skip the gates.

---

## 0. What we are building (one paragraph)

TracePilot takes the telemetry of a distributed system (traces, logs, metrics, deploy events), reconstructs what happened during an incident, generates competing root-cause hypotheses, **tests them against real evidence**, and reports a diagnosis in which every claim is backed by cited evidence. Then the engineer can ask "what if we had changed X?" and TracePilot **replays the recorded workload through a deterministic simulation** of the system with the change applied, and shows before/after results.

This is a **scoped MVP**: one fully working end-to-end scenario (DB connection-pool exhaustion), built on a simulated e-commerce backend, with a CLI first and a web UI second. Real integrations (OpenTelemetry, Prometheus, a real Kubernetes cluster, etc.) are explicitly out of scope, but the data schemas should be OTel-shaped so they can be added later. Kubernetes *concepts* (replicas, pod events, OOMKills, rollouts) are simulated inside `sim`, not integrated.

### The three rules that decide every design choice

1. **Numbers never come from the LLM.** Every latency, rate, count, timestamp or metric shown anywhere (UI, report, agent output) must come from a deterministic tool or the simulator. The LLM orchestrates and reasons; it never fabricates or "predicts" metrics.
2. **No claim without evidence.** Every statement in a diagnosis is typed `FACT`, `INFERENCE` or `HYPOTHESIS`, and a deterministic verifier rejects anything whose cited evidence does not exist or does not match.
3. **No hardcoded demo.** The investigation must run for real against the telemetry store. Recorded LLM transcripts ("cassettes", see §8) are allowed for tests and offline demos, but must be real past runs and labeled as recorded in the UI.

### Honest framing (put this in the README)

The telemetry in the demo is **synthetic**, generated by our own simulator. To avoid grading our own homework:
- The investigator can only reach telemetry through query tools. It never sees simulator config or the incident ground truth.
- Ground truth lives in a separate file used only by the eval harness.
- We ship at least one scenario with **red herrings** and ideally three different incident types (§5).
- The replay is a **model of system behavior, not a guarantee** of production behavior. The UI must say so near every replay result.

## 1. Tech stack (defaults, change only with a written reason in NOTES.md)

- TypeScript (strict, no `any`), Node 20+, pnpm workspaces monorepo.
- Validation: Zod for every boundary (telemetry, tool I/O, agent output, API).
- Storage: SQLite (`better-sqlite3`) for the telemetry store and incidents.
- Server: Hono or Fastify, REST + Server-Sent Events for streaming investigation steps.
- Web: React + Vite + Tailwind. Service graph with React Flow. Time-series charts with uPlot or Recharts.
- LLM: `@anthropic-ai/sdk` with tool use. Model from env `TRACEPILOT_MODEL` (default `claude-sonnet-5-5`; `claude-opus-5-5` for the final verification pass if configured). API key from env `ANTHROPIC_API_KEY`.
- Tests: Vitest. Property-style tests where useful (fast-check optional).
- No Python needed. No Docker needed for MVP.

### Monorepo layout

```
tracepilot/
  packages/
    schema/      # Zod schemas + TS types for spans, logs, metrics, events, topology, evidence, diagnosis
    sim/         # deterministic discrete-event simulator, scenarios, workload recorder
    store/       # SQLite telemetry store + typed query API (the ONLY way agents read data)
    analysis/    # pure deterministic analyzers (timeline, anomaly, dependency, propagation, saturation)
    agents/      # LLM orchestration: tools, evidence ledger, hypothesis engine, skeptic, verifier, cassettes
    cli/         # `tracepilot` command
  apps/
    server/      # API + SSE
    web/         # UI
  eval/          # eval harness + ground-truth files (agents must not import this)
  NOTES.md       # decision log, updated at the end of every phase
  README.md
```

Enforce the "agents never see ground truth or sim config" rule with an ESLint `no-restricted-imports` rule: `packages/agents` and `apps/server` may not import from `eval/` or from `sim` internals (only the `schema` package and `store`).

## 2. Data model (OTel-shaped, simulated time)

All timestamps are **virtual time** in integer microseconds from simulation start. Never use `Date.now()` or `Math.random()` anywhere in `sim/` or `analysis/`.

- **Span**: `traceId, spanId, parentSpanId, service, name, startUs, endUs, status (ok|error|timeout), attributes{}`.
  Include explicit child spans for waiting: `db.pool.acquire` (duration = time waiting for a connection), `db.query` (duration = execution), `queue.wait`. Attributes on these (pool size, in-use at acquire time) are what make root cause discoverable.
- **LogRecord**: `ts, service, level, message, fields{}, traceId?`. Logs must be realistic and mostly noisy-but-true (e.g. "timeout acquiring connection after 5000ms", "request exceeded deadline"). Include some irrelevant noise logs.
- **MetricPoint**: `ts, service, name, value, labels{}`, sampled every 5s virtual time. Required metrics per service: `request_rate`, `error_rate`, `latency_p50/p95/p99`, `in_flight`, `queue_depth`. For DB: `pool_in_use`, `pool_capacity`, `pool_wait_queue`, `query_exec_p95`, `db_active_queries`.
- **ChangeEvent**: `ts, kind (deploy|config|rollout), service, description, diff{key: {from, to}}`.
- **PodEvent** (Kubernetes-style, simulated): `ts, service, pod, reason (Scheduled|Started|OOMKilled|Restarted|CrashLoopBackOff|ReadinessFailed|Evicted), message`. Used by the pod-lifecycle scenario (§5, Scenario D). Extra metrics for it: `replicas_ready`, `pod_restarts`, `memory_working_set`, `cpu_throttled_ratio`.
- **Evidence ID**: every stored item gets a stable ID (`sp_…`, `lg_…`, `mt_<service>_<metric>_<ts>`, `ev_…`). Agents cite these.

The simulator writes these into the store through the same schema validation any future real ingestor would use.

## 3. Simulator (`packages/sim`) — the heart of the product

A **discrete-event simulation** with a virtual clock and a seeded PRNG (e.g. mulberry32/PCG). It must be:

- **Deterministic**: same scenario + seed + workload ⇒ byte-identical telemetry (test by hashing).
- **Common-random-numbers safe**: each request gets its own PRNG stream derived from `(seed, requestId)`, and each random draw inside a request is keyed by a stable label (e.g. `checkout.cpu`, `db.query.3`). Changing capacity or timeouts must NOT change the random draws of unrelated requests. This is what makes counterfactual comparison meaningful: differences come from the change, not from noise.
- **Workload-separated**: a `Workload` is a recorded list of `{requestId, arrivalUs, type}` (plus the seed). Generating a workload and running it are separate steps, so the same workload can be replayed against different system configs.

### System model (declarative, JSON/TS)

Services with: `replicas` (N identical pods, each with its own `workers` and queue, load-balanced round-robin; **support `replicas` from Phase 1 as a static knob**, default 1), `workers` (max concurrency per replica), `queueLimit`, `serviceTimeDist` (lognormal/exponential params per operation), `timeoutUs`, `retryPolicy` (optional, default none).
Request types as call graphs, e.g. `checkout: gateway → checkout → [inventory.reserve, payment.charge] → db`.
**Database model**: connection pool (`capacity`, FIFO wait queue, `acquireTimeoutUs`) **plus** a DB executor with `maxParallelQueries`. Query time = base execution time; when active queries exceed `maxParallelQueries`, queries queue at the DB. This matters: enlarging the pool is not free, because the bottleneck can move to the DB.
Optional later: cache with capacity and hit-rate model.

### Supported counterfactual knobs (all must work in the engine)

- `db.pool.capacity`
- `<service>.workers` (concurrency per replica)
- `<service>.replicas` (pod count; Kubernetes-style scale out/in)
- `<service>.memoryLimit` / `<service>.cpuLimit` (only once pod lifecycle exists, Scenario D)
- `<service>.timeoutUs`, `db.acquireTimeoutUs`
- `<queue>.consumers` / `queueLimit`
- `cache.capacity` (only if cache implemented)
- `revert <changeEventId>` (undo a recorded deploy/config diff)

### Validity tests (required, these gate Phase 1)

1. **Determinism**: same inputs twice ⇒ identical output hash.
2. **Identity replay**: replaying the recorded workload with NO modifications reproduces the recorded telemetry exactly. If this fails, the replay engine is not trustworthy.
3. **Monotonicity**: increasing pool capacity never increases total acquire-wait time for the same workload (up to DB-executor effects, which must be tested separately and explained).
4. **Conservation / Little's law sanity**: average in-system ≈ throughput × average latency within tolerance on steady-state windows.
5. **Isolation of randomness**: changing `db.pool.capacity` leaves every request's drawn service times unchanged.

## 4. Analysis library (`packages/analysis`) — deterministic, pure, heavily tested

Pure functions over data returned by the store. No LLM, no I/O. Each returns structured results that include the evidence IDs behind every number.

1. **Timeline builder**: merges change events, metric anomalies, error-log bursts, and span-level changes into one ordered timeline.
2. **Anomaly detector**: per metric series, compare against a baseline window using robust statistics (median/MAD) plus a change-point method (CUSUM or similar). Output: onset time, magnitude, direction, confidence, evidence IDs. Must not flag the red herrings as incident-causing without context.
3. **Dependency graph**: derived from spans (not from sim config). Edges with call counts and latency.
4. **Latency attribution**: for a slow trace set, break time into `queue wait / pool acquire wait / query exec / downstream call / own compute` per service. This is the key tool that separates "DB is slow" from "waiting for DB connections".
5. **Saturation analysis** (USE method): utilization, saturation (queue depth), errors per resource; flags resources at ≥95% utilization with growing queues.
6. **Propagation analysis**: orders anomaly onsets along the dependency graph; checks temporal precedence (a cause must start before its effects) and walks failure paths from root to user-facing symptom.
7. **Change correlation**: for each change event, did anomaly onsets in related services follow within a plausible lag? Reports correlation, never claims causation.

Each analyzer needs unit tests on synthetic series with known answers, including a negative case (no anomaly) and a noisy case.

## 5. Scenarios

All scenarios share the same topology: **API Gateway → Checkout → (Inventory, Payment) → Database**, with one DB connection pool shared by Checkout/Inventory/Payment.

### Scenario A (required): `pool-exhaustion`

- Baseline: ~80 checkout req/s, pool utilization ~35–45%, checkout p99 ~100–150 ms, error rate ~0.
- Change event at T+10 min: `checkout v2.4.1` deploy that raises worker concurrency 20 → 60 and increases per-request DB connection demand (parallel inventory-reservation queries, fan-out ×4). Pool capacity stays 30.
- Expected incident: pool hits 100%, wait queue grows, `db.pool.acquire` span durations balloon, checkout p99 reaches multiple seconds, requests start hitting the 5s timeout, error rate climbs, gateway shows 5xx. DB query **execution** time stays roughly flat (this is the discriminating fact against "DB is slow").
- **Red herrings** (must exist): (1) an unrelated `inventory` config tweak a few minutes before the incident with no real effect; (2) a short, self-resolving payment-service latency blip ~3 minutes before the incident.
- Calibrate parameters with a script and **assert these characteristics in tests**. If the model does not produce the expected behavior, fix the model's realism. Do not fudge numbers.
- Expected qualitative replay outcomes (verify the sim produces them honestly): pool 30→64 resolves the incident; reverting the deploy resolves it; reducing checkout workers 60→20 mostly resolves it by shedding load earlier; increasing timeouts alone makes things worse; a very large pool shows the bottleneck moving to the DB executor.

### Scenario B (stretch): `slow-dependency-retry-storm`
Payment service gets slow, checkout retries amplify load, thread/worker exhaustion in checkout. Root cause differs from A, so the investigator can't pattern-match on "pool".

### Scenario C (stretch): `cache-hit-rate-drop`
A deploy changes a cache key, hit-rate collapses, DB load rises, latency climbs.

### Scenario D (stretch, Kubernetes-flavored, simulated only): `bad-rollout-oomkill`
A rollout of `checkout` raises per-request memory use. Pods hit their memory limit, get `OOMKilled`, restart, and enter `CrashLoopBackOff`. `replicas_ready` drops, remaining pods take more load, latency climbs, errors follow. Needs a small pod lifecycle model in `sim` (memory growth per in-flight request, limit, kill, restart delay with backoff, readiness). Discriminating evidence: pod events and restart counts precede the latency rise; DB pool is NOT saturated (a red herring against Scenario A's pattern). Expected replay outcomes: raising `checkout.memoryLimit` or reverting the rollout resolves it; adding replicas only delays the failure. This stays an in-simulator model. Do not connect to a real cluster.

Each scenario ships with a `ground-truth.json` in `eval/` (root cause, causal chain, correct fix) that the agents never read.

## 6. Agent layer (`packages/agents`)

### Principle
Deterministic analyzers do the finding. LLM roles do the reasoning over their outputs. Prefer **one tool-using investigator loop + a skeptic + a verifier** over six independent chatty agents. The UI may present the analyzers and roles as named "analysts" (Timeline, Dependency, Anomaly, Hypothesis, Skeptic, Verifier) because that is a clear mental model, but implementation stays simple.

### Tools exposed to the LLM (thin wrappers over `store` + `analysis`)
`get_incident_window`, `list_change_events`, `get_metric_series`, `detect_anomalies`, `build_timeline`, `get_dependency_graph`, `attribute_latency`, `get_saturation`, `analyze_propagation`, `search_logs`, `get_trace`, `compare_windows`. All return data with evidence IDs. Tool outputs are the only source of facts.

### Evidence ledger
A structured ledger where every entry is one of:
- `FACT`: directly read from a tool result. Must cite evidence IDs; value/time must match the stored data.
- `INFERENCE`: derived from FACTs by a named rule (e.g. "onset order along dependency edge"). Must list premise entry IDs.
- `HYPOTHESIS`: unverified. May not be used as a premise of a FACT.

### Hypothesis engine
1. Investigator builds the timeline and anomaly picture, then proposes **3–5 competing hypotheses**, each with **testable predictions that discriminate between hypotheses** (e.g. pool exhaustion predicts: acquire-wait dominates latency attribution AND query exec time flat AND pool utilization ≈100% before latency rises; slow-DB predicts: exec time up; slow-downstream predicts: payment spans up).
2. Each prediction is checked by running tools. Result: `supported / contradicted / inconclusive` plus evidence IDs. Hypothesis scores come from these results, not from the LLM's self-reported confidence.
3. **Skeptic** (separate prompt, separate context): receives the leading hypothesis and the evidence, must (a) run at least N new discriminating queries trying to disprove it, (b) propose the strongest alternative explanation, (c) check red herrings and temporal precedence. Its findings are written to the ledger.
4. **Verifier**: first a deterministic pass (every cited ID exists; every quoted number/time matches the store within tolerance; no HYPOTHESIS used as FACT premise; temporal precedence holds for the causal chain). Then an LLM pass for logical support. Any failure sends the diagnosis back for revision, and the failure is shown in the UI. Max 2 revision rounds, then publish with unresolved issues clearly listed.

### Diagnosis output (Zod schema)
`rootCause`, `causalChain[]` (ordered, each step citing ledger entries), `affectedServices`, `rejectedHypotheses[]` (with the evidence that rejected them), `confidence` (computed by a rubric from prediction results and unresolved contradictions, not LLM-stated), `unknowns[]`, `recommendations[]` where each recommendation includes a **machine-readable patch** (e.g. `{target:"db.pool.capacity", from:30, to:64}`) that can be fed straight into the replay engine.

### Safety
Read-only. TracePilot never changes infrastructure. Recommendations are suggestions that a human can try in replay.

## 7. Counterfactual replay

Input: incident id + list of patches. Process: load the recorded workload and system model from the incident, apply patches, run the **same simulator** with the same seed and per-request random streams, store results as a replay run.

Output compares original vs replay on: latency p50/p95/p99 over time, error rate, throughput, resource utilization, queue depth, and **which services failed or timed out** (propagation). Also compute headline deltas (e.g. "incident duration", "requests failed") from the data.

Extras (cheap because the sim is deterministic):
- **Sweep**: run a parameter range (e.g. pool capacity 20..120) and chart p99 / error rate against it, showing the knee and where the DB executor becomes the new bottleneck.
- **Side-effect panel**: after any replay, run the saturation analyzer on the replayed telemetry and surface any new bottleneck it created.
- The LLM may *suggest* patches and *narrate* replay results using only returned numbers, but it never produces the numbers.

Every replay screen shows: "Simulated from a model of the system. Not a guarantee of production behavior."

## 8. LLM cost control and cassettes

- Provider wrapper around the Anthropic SDK with: request/response logging, token + cost counters per investigation, and a hard `MAX_TOKENS_PER_INVESTIGATION` budget from env.
- **Cassette mode**: record real LLM request/response pairs to disk keyed by a hash of the request. `TRACEPILOT_LLM=live|record|replay`. Tests and CI use `replay`. The UI shows a "Recorded run" badge when a cassette is used. Never hand-write cassettes.
- Keep tool results compact (summaries + evidence IDs, not raw dumps) to keep context small.

## 9. Interfaces

### CLI (build and finish this before the UI)
```
tracepilot sim run --scenario pool-exhaustion --seed 42 --out .data/
tracepilot investigate --incident <id> [--stream]
tracepilot replay --incident <id> --patch db.pool.capacity=64
tracepilot replay --incident <id> --revert <changeEventId>
tracepilot sweep --incident <id> --param db.pool.capacity --range 20:120:10
tracepilot eval --scenario pool-exhaustion
```

### Web UI (low text, high clarity; dark, technical, restrained)
1. **Overview**: system health, service graph (React Flow) colored by health, active incidents, recent deploys.
2. **Incident page**: timeline (changes, anomalies, errors on one axis), affected services, click a service to see its metrics and related traces.
3. **Investigation view**: streams the investigation live. Hypothesis board with status chips (supported / contradicted / inconclusive), the skeptic's challenge, verifier results, and the final diagnosis. Every claim has a chip that opens the underlying evidence (span, log, or metric) in a side panel.
4. **Replay lab**: knobs (sliders/inputs for the supported parameters), Run, then synchronized before/after charts, headline deltas, side-effect warnings, and a sweep chart. The "simulated model" notice is always visible.

Keep copy minimal. Prefer charts, chips and short labels over paragraphs.

## 10. Evals and tests

- **Unit tests**: every analyzer, store queries, schema validation.
- **Sim validity tests**: §3 (determinism, identity replay, monotonicity, Little's law, random isolation). These are the most important tests in the repo.
- **Verifier tests**: fabricated citation rejected; wrong number rejected; HYPOTHESIS used as FACT premise rejected; effect-before-cause chain rejected.
- **Agent eval harness** (`eval/`): runs the investigation (live or cassette) on each scenario and scores against `ground-truth.json`: root-cause match, **evidence validity rate must be 100%**, hallucination count must be 0, red herrings not blamed, skeptic produced at least one real challenge, recommended patch actually improves the replay.
- Report eval results in the README as a table (be honest about failures).

## 11. Build phases

Models noted are recommendations for the human, not constraints on code. **Fable** = use the strongest model for the hard core while the offer lasts. **Opus** = fine for the rest. Phases 1–4 are the high-value, high-risk core; do these first.

| # | Phase | Model |
|---|-------|-------|
| 0 | Scaffold: monorepo, schema package, lint rules, CI script, NOTES.md | Opus |
| 1 | Simulator + scenario A + sim validity tests (§3, §5) | **Fable** |
| 2 | Store + analysis library + tests (§4) | **Fable** (design) / Opus (fill-in tests) |
| 3 | Agent layer: tools, ledger, hypothesis engine, skeptic, verifier, cassettes, CLI `investigate` (§6, §8) | **Fable** |
| 4 | Counterfactual replay + sweep + CLI (§7) | **Fable** |
| 5 | Server + web UI (§9) | Opus |
| 6 | Scenarios B/C/D (D adds the pod lifecycle model), eval harness, README, demo script, polish | Opus |

### Gates (do not start the next phase until the gate passes)

- **Gate 1**: all §3 validity tests green; scenario A produces the expected incident characteristics; red herrings present.
- **Gate 2**: analyzers correctly find the root-cause signals on scenario A (pool saturation precedes latency rise; acquire-wait dominates attribution; DB exec time flat) without any LLM.
- **Gate 3**: `tracepilot investigate` on scenario A returns a diagnosis that passes the verifier, rejects at least the "slow DB" alternative with cited evidence, and does not blame the red herrings.
- **Gate 4**: replay of the recommended patch improves the metrics; identity replay still exact; sweep shows a sensible knee.

At the end of each phase: run all tests, commit, and append decisions, assumptions and known gaps to `NOTES.md`.

## 12. Working rules for Claude Code

- Strict TypeScript, Zod at boundaries, no `any`, no silent catches.
- No wall-clock time or `Math.random()` in `sim/` or `analysis/`. Lint for it.
- Never let model output flow into a number shown to the user. If in doubt, the number comes from a tool.
- If a test reveals the model is unrealistic, fix the model. Do not tune numbers just to hit the expected demo output.
- Keep the agent prompts in versioned files under `packages/agents/prompts/` with a short rationale comment each.
- If something in this brief is contradictory or infeasible, write the problem and your decision in NOTES.md and continue with the most defensible choice. Ask the human only for decisions that are hard to reverse.
- Do not add real cloud integrations, auth, multi-tenancy, or autonomous remediation. They are non-goals.

## 13. Definition of done (MVP)

1. `tracepilot sim run` generates scenario A; the incident is visible in the store.
2. `tracepilot investigate` produces a verified, evidence-cited diagnosis, rejecting alternatives and ignoring red herrings, with no hardcoded outputs.
3. `tracepilot replay` and `sweep` compare the original incident to modified runs using only simulator-computed numbers; identity replay is exact.
4. The web UI shows service graph, incident timeline, live investigation with clickable evidence, and the replay lab.
5. All validity, verifier and analyzer tests pass; eval table in README with honest results.
6. README explains the architecture, the three core rules, the synthetic-data caveat, and non-goals, and includes a 2-minute demo script.
